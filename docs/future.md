# 后续阶段草案（不具规范效力）

这里收着 v0.4 写进规范、v0.5 移出来的内容，以及做 Phase 1 时冒出来但不该现在做的想法。它们是**待验证的草案**：进入对应阶段时要重新设计、补黄金用例，再写进 [SPEC.md](../SPEC.md)。v0.4 的完整文本在 git 历史里（提交 `4168a00`）。

每一节末尾列出「进规范前要先回答的问题」。

## 1. 观察范围 O2：整个 Agent

想观察的事件：子 Agent 完成、后台任务结束或就绪、任务看板状态变化、会话切换。v0.4 给出的事件草案：

```ts
{ type: 'agent.subagent_completed'; subagentId; goal?; status: 'completed'|'failed'|'interrupted'; summary?; at; sessionId? }
{ type: 'agent.background_job'; jobId; command?; status: 'completed'|'failed'|'ready_match'; exitCode?; summary?; at; sessionId? }
{ type: 'agent.task_updated'; taskId; status; pendingReviews?; openTasksCount?; at; sessionId? }   // 计数由宿主权威上报
```

v0.4 为它们定过三条规则，方向仍然合理：

- **时效**：「最近一次」类信号带时间戳，超过窗口（当时取 60 秒）就视为缺失，否则会永远命中。
- **单次消费**：一个触发事件只触发一次求值。
- **会话归属**：事件自带 `sessionId`，否则归到上报通道所在的会话。

v0.5 已经为它们铺好的路：未知类型的事件被接收后忽略；空结果不再让在场的建议失效（v0.4 里每个落空的环境事件都会清掉当前建议）。

进规范前要先回答：

- 没有「当前轮次」时，建议钉在什么上面？发送的轮次核对（SPEC §5.3）怎么表述？
- 触发事件到达时某个回合正在运行，是丢弃、排队还是合并？
- 这类建议放在哪个会话的界面上，用户才不会觉得串了台？

## 2. 观察范围 O3：工作台环境

终端命令、Git 状态、文件变更、IDE 焦点与诊断、剪贴板类别。v0.4 的要点：每类观察器单独开关，关掉即不产生事件；自由文本（命令原文、摘要、剪贴板预览）不进入发给模型的信号摘要，只允许枚举和计数。

进规范前要先回答：

- 观察器由谁实现、怎么取得用户同意，装了之后用户怎么知道它在看什么。
- 环境触发天然高频、低相关。先在检查面影子统计误报率，再决定要不要给用户看。

## 3. 行动力 A2：推测预执行

建议还挂着的时候，宿主在后台跑只读的准备工作（预取文件、跑 `git diff`），用户一发送就接近立刻有结果。执行方是宿主，核心只给计划。

进规范前要先回答：「只读」由谁判定、怎么测；无谓预跑的成本；用户开始下一轮时怎么保证全部停下。

## 4. 行动力 A3：委托执行

用户在卡片上确认后，直接派发 `tool` / `custom` 类动作，而不是发一条消息让 agent 自己去做。v0.5 里这两类动作只是元数据。

进规范前要先回答：每次派发的证据链（谁确认、派发了什么、结果如何）；误派发的回归用例；与宿主自身审批流的关系。

## 5. 宿主原生界面

协议已经允许宿主声明 `capabilities.surface` 自己呈现建议。缺的是配套动作：建议被采纳进宿主输入框、由用户按回车发出时，没有经过核心的派发，现在只会被记成相似度为 1 的 `passed`。需要一个「已被界面采纳」的动作，以及输入框非空时不出建议之类的界面侧约定。

这是 Phase 2 最值得先做的一件事：建议出现在用户正要打字的地方时使用率是多少，决定了这个功能的上限。

## 6. 打分：先验、融合、校准

v0.4 的对数线性融合（模型置信度、场景先验、结构加分）与分差门槛被整体移除，原因见 [review-issues.md](review-issues.md) R29：公式算不出它声称的结果，常数没有来源。

有了回放数据之后，可以依次尝试、每次只加一样：

1. 按场景统计的先验（来自数据，而不是作者估计）。
2. 置信度校准（自报值 → 实际命中率的映射）。
3. 两个候选合起来才过线时出多选卡（`P(i₁) + P(i₂)` 的门槛）。v0.4 想用分差门槛表达这一点，但分差小的时候建议是被压掉而不是变成多选。

## 7. 在线学习

v0.4 的「连续被忽略就抬高阈值」依赖字面相似度推断的负例，已停用。重新启用前要先证明：相似度判为未命中的样本里，意图确实没命中的比例足够高。更可靠的做法是把真实下一句离线标注到目录里（回放工具里的评审模型），再用标注结果更新先验。

## 8. 模型生成的建议文字

v0.4 允许 `render: { mode: 'model' }`，并配了 9 条针对模型文字的过滤（空或元文本、标签前缀、助手口吻、纯寒暄、多句、带格式、长度、报错文本、危险命令）。v0.5 只有模板，这些规则中与模板作者有关的部分留在 `tools/validate.py` 里当场景包的写作检查。

重新引入的理由只可能是：模板的话太泛，用户不愿意用。那需要先有使用数据，并且把「模型的字上屏」带回来的注入面重新评估一遍。

## 9. 其他

- **`fork` 采样的更多宿主**：协议已定义，目前没有宿主实现它。Codex 的 `thread/sample` 是现成的对应物。
- **多宿主共用一个核心与界面**：现在每个宿主进程各起一个 sidecar，各有一个页面地址。
- **打字中的草稿路由**（Qwen Web Shell 式）：对正在输入的内容做保守分类。不在五个阶段内。
- **遥测持久化与导出**：现在只追加写本地 JSONL。
